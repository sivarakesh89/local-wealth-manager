# FinMate v3.45.0 — Recovery Import Build

This is a dedicated recovery-testing build based on FinMate v3.44.0. It is intended for isolated, local recovery testing—not as a general release.

## Recovery import changes

- The encrypted-vault import flow asks for the recovery file's master password before parsing/decrypting the file, rather than first attempting decryption with the currently open vault's key.
- Large files over 20 MiB show a laptop/desktop-only warning and an explicit memory-risk notice.
- Import requires two confirmations, including a warning that the vault in the current browser profile will be replaced.
- After successful password unwrap and AES-GCM authentication, the encrypted record is stored directly in IndexedDB. The importer does not re-encrypt or serialize the decrypted vault before storing it, reducing one major source of transient memory pressure.
- No Google Drive sync or upload is triggered by recovery import.
- The imported encrypted record's payload and wrappers are retained as received; original source files are not modified.

## Limitations

- The file must still be read and parsed as JSON, and the encrypted payload must be decrypted into memory. The 155 MB gold-media file can still exceed browser memory, even on a laptop. If the browser becomes unstable, stop and do not repeatedly retry.
- This build has only been statically checked in this environment. It has not been browser-tested against the user's recovery files or password; the recovered files were not present in the working directory.
- Test the lightweight vault first in a separate Chrome profile. Only attempt the gold-media vault after the lightweight vault opens and the basic records are verified.
- Do not use the user's only working browser profile. Do not sync to Drive until verification and a fresh encrypted backup are complete.
