# FinMate v3.66.3 — Serialized journal writes

## Why this patch exists

A successful Drive retrieval clears the local change journal. A journal write that began before retrieval could still be in flight and finish after that clear, making old pending entries reappear. Version 3.66.2 guarded journal generation with an epoch, but it did not serialize the IndexedDB write itself against the clear operation.

## Fix

- Serialize encrypted journal writes and journal clears through one promise queue.
- A clear waits for journal writes already queued before it, then writes the empty journal as the final queued mutation.
- Retrieval's epoch/suppression guard remains in place to prevent new stale diffs from being queued during replacement.
- No journal entries are deleted except when the existing upload/retrieval flow explicitly acknowledges or replaces them.
- No changes to the vault data model, Drive OAuth, shared baseline, or media store.

## Regression test

1. Keep the previous ZIP and a current encrypted backup. Do not clear browser storage.
2. Deploy the ZIP contents and confirm About reports v3.66.3.
3. Unlock, upload core + media, publish the shared baseline, and reload. Pending journal should remain 0.
4. Retrieve from Drive and wait for the success message.
5. Confirm pending journal remains 0 immediately after retrieval and after another reload/unlock.
6. Add one harmless test record and confirm the pending journal becomes nonzero, then upload and verify it returns to 0.
7. Verify several records and any jewellery photos/invoices.

Static checks do not constitute a live Google Drive test. Do not clear IndexedDB or manually delete journal data if the issue persists; capture the displayed count and console error instead.
