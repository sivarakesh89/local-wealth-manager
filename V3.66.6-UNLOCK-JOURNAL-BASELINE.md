# FinMate v3.66.6 — Unlock Journal Baseline Fix

## Fix

The first unlock path now suppresses journal-diff creation while it performs startup migration, persists the normalized vault, and generates due recurring transactions. The suppression is restored in a `finally` block even if startup work throws. The same startup guard is applied to master-password, legacy-vault migration, PIN, and biometric unlock paths.

This prevents startup/deploy initialization work from being misclassified as dozens of user-edited records. It does **not** delete or clear an existing journal, reset pending entries, or change the upload acknowledgement flow. Ordinary user edits after unlock continue to be journaled.

## Safety

- Keep the previous ZIP and a current encrypted backup.
- Do not clear browser storage or IndexedDB.
- Existing pending entries are preserved; upload/verification remains the way to acknowledge them.
- This build has passed static checks only. It has not been tested against the user's live Google Drive account.

## Regression checklist

1. Deploy v3.66.6 and unlock. Record pending count; startup must not create a large new backlog.
2. Reload and unlock without edits; pending count must remain unchanged.
3. Add one harmless test transaction; pending count should rise by one effective record.
4. Edit that transaction; pending count should remain one.
5. Upload and verify; pending count should return to zero.
6. Reload and unlock; pending count should remain zero.
7. Retrieve after reload and Google authorization; verify pending count remains zero.
8. Repeat initial unlock with PIN or biometric if those methods are enabled.

If the count is nonzero immediately after deploying, do not delete it. Record the count before and after a second reload/unlock; existing journal entries may be preserved from the prior version.
