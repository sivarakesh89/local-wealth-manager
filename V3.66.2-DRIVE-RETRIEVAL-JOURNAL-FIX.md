# FinMate v3.66.2 — Drive Retrieval Journal Fix

## Problem addressed
After a verified upload and a clean reload, retrieving the same encrypted vault could cause the local pending journal to repopulate. This undermined the clean-journal guard and could block later retrieval attempts.

## Change
- Adds a journal epoch guard so an in-flight journal diff started before a vault replacement cannot write stale entries after retrieval begins.
- Suppresses new local journal diffs while the Drive vault and its metadata are being restored.
- Clears the journal only after the retrieved core vault has been persisted and media retrieval has completed.
- Reads the journal back after clearing and verifies that the pending count is zero before reporting successful retrieval.
- Keeps the existing recovery-point creation, encrypted vault format, media store, and pending-change protection for the start of retrieval.

## Test procedure
1. Keep the v3.66.1 ZIP and a current encrypted backup. Do not clear browser storage.
2. Deploy the contents of this ZIP to the same GitHub Pages location, replacing app files only.
3. Confirm About → Version shows `3.66.2`.
4. Unlock, make a small test edit, upload core + media, and verify pending changes become `0`.
5. Reload and unlock; confirm the count stays `0`.
6. Retrieve from Drive and approve the replacement confirmation.
7. Confirm retrieval reports local pending journal verified at `0`.
8. Reload and unlock again; confirm the count remains `0` if no new records were changed or newly generated.
9. Check several records and any jewellery/property photos or invoices.

## Safety notes
- Do not manually delete IndexedDB/site storage or journal data.
- Retrieval still creates a local recovery point before replacing the vault.
- The app performs static checks only in this build environment; live Google Drive behavior must be confirmed in the user's browser.
