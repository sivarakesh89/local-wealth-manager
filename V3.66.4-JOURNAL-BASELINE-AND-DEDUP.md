# FinMate v3.66.4 — Journal baseline and deduplication

## Fixes
- On successful password, PIN, or biometric unlock, save the migrated/normalized vault as a non-journaled baseline before generating due recurring transactions. This prevents migration-only field normalization from being misreported as dozens of user changes after reload/OAuth authorization.
- Store one pending journal entry per collection + record ID rather than appending duplicate entries for repeated edits to the same record.
- Preserve create semantics when a pending create is edited; cancel a pending create if it is deleted before synchronization.
- Retain serialized journal writes/clears and retrieval suppression safeguards from v3.66.3.

## Expected checks
1. Keep the prior ZIP and a current encrypted backup. Do not clear browser storage.
2. Deploy the ZIP contents and confirm About reports v3.66.4.
3. Unlock without editing data: pending changes should stay at 0.
4. Add one transaction: pending changes should become 1. Edit that same transaction again: it should remain 1. Delete it before upload: pending changes should return to 0 if it was created after the last sync.
5. Upload core + media, publish shared baseline, reload, and confirm 0.
6. After reload, click Retrieve from Drive, complete Google authorization and master-password unlock. Retrieval should complete with pending changes at 0, and remain 0 after another reload.
7. Verify existing records and jewellery photos/invoices.

Static checks are not a live Google Drive test. Do not clear IndexedDB/site storage or manually delete journal data. If the counter is still wrong, capture the exact count and browser console error.
