# FinMate v3.66.0 — End-to-end validation and release candidate

## Why this release exists
This is the final planned milestone, not another feature-development milestone. It packages the previously tested conflict review, local-only conflict application and audit trail, audit viewer/fingerprint, manifest verification, and verification receipt in one versioned release. It does not intentionally change sync, conflict-resolution, vault, or media behavior.

## Deployment
1. Keep all earlier ZIPs and backups unchanged.
2. Deploy the contents of this ZIP to the existing GitHub Pages repository (replace deployed app files, but do not delete browser storage or IndexedDB).
3. Hard-refresh/reopen the PWA and confirm About → Version is `3.66.0`. If the old version remains, close installed tabs and reopen after the service worker updates; do not clear site data.

## Final acceptance checklist
### A. Core vault and privacy
- [ ] Unlock the existing vault with the existing master password/PIN flow.
- [ ] Confirm existing financial entries, jewellery photos/invoices, and real-estate attachments remain visible.
- [ ] Confirm pending-change count matches the pre-update value.
- [ ] Confirm no entry was added, removed, or overwritten by opening audit tools.

### B. Google Drive and baseline safety
- [ ] Run Google diagnostics and confirm authorization is healthy.
- [ ] Use the established read-only Drive compare/review flow; verify it does not upload, pull, or apply records by itself.
- [ ] Confirm shared baseline is unchanged during read-only review.
- [ ] Do not run a real push/pull merely to test audit viewer or receipt functionality.

### C. Conflict workflow
- [ ] Open a saved conflict worksheet and verify unresolved decisions remain blocked from application.
- [ ] Confirm stale worksheets are rejected.
- [ ] If testing local apply, use a deliberate test conflict and confirm a recovery point is created first. Remember that KEEP_DRIVE applies to this device only; it does not sync the result back to Drive.
- [ ] Confirm the audit report records decisions and before/after hashes without embedding financial record contents.

### D. Audit evidence workflow
- [ ] Open a valid v3.60.0 audit JSON and confirm its SHA-256 fingerprint is stable across reopening.
- [ ] Export HTML and confirm it carries the same fingerprint.
- [ ] Export a verification manifest and confirm all seven checks pass against the same report.
- [ ] Verify a changed fingerprint and a changed summary count; both should show MISMATCH.
- [ ] Export a verification receipt for MATCH and MISMATCH cases; confirm individual check results are included and financial vault contents are absent.
- [ ] Test invalid JSON, malformed hashes/counts, unrelated files, and picker cancellation.

### E. Recovery and media
- [ ] Confirm recovery points are still listed.
- [ ] Confirm jewellery and real-estate attachments display.
- [ ] Do not import recovery media shards or restore a backup unless explicitly testing recovery with separate copies.

### F. Final non-regression snapshot
Before and after the checklist, compare: vault entries, pending-change count, Drive files/state, shared baseline, and media. They should remain unchanged unless you deliberately performed and documented a test action that modifies local records.

## Scope and honest limitations
- Static packaging checks are run before delivery; this environment cannot certify the user's live GitHub Pages deployment, browser IndexedDB state, OAuth session, or Google Drive state. The user-run checklist above is the acceptance test for those.
- A matching SHA-256 fingerprint/manifest is a consistency check, not a digital signature or proof of authenticity.
- Conflict worksheet application remains local-only. Do not interpret it as a cloud merge or as a completed two-way record sync.

## Release policy
This is the final planned milestone from the five-milestone roadmap. After this release, the roadmap is complete when the checklist passes. Further releases should be limited to a confirmed defect, a security issue, or a specifically requested new capability—not more incremental audit sub-milestones.
