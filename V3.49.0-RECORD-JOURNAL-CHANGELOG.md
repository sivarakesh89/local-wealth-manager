# FinMate v3.49.0 — Record Journal & Pull Conflict Guard

## Purpose
Build a safe foundation for later record-level incremental synchronization without changing the working secure Google OAuth flow, encrypted core-vault format, or separate encrypted media store.

## Included
- Adds an IndexedDB `syncmeta` store through a database version upgrade; existing vault, media, and recovery stores are retained.
- Assigns stable UUIDs to records in supported top-level collections when records lack IDs.
- Records local create, update, and delete operations by comparing the active profile with the previous encrypted local vault snapshot.
- Stores the change journal encrypted with the unlocked vault's AES-GCM key. Journal entries contain collection, stable record ID, operation, timestamp, and device ID; deleted records are represented as tombstones.
- Caps the journal at 5,000 most-recent entries to avoid unbounded growth.
- Displays a pending-local-change count in the Google Drive status panel.
- Blocks Drive retrieval while local journal entries are pending, preventing a whole-vault pull from silently discarding locally changed or deleted records.
- Clears the local pending journal only after a Drive core upload has been read back and successfully decrypted, or after a retrieval has completed.
- Keeps local journal metadata separate from the Drive vault payload. This is a local change-tracking foundation, not yet cross-device record-level merge.

## Still planned
- Persist a per-record common ancestor/baseline across devices.
- Compare remote and local record versions and show a conflict-resolution UI.
- Synchronize individual changed records and tombstones instead of replacing the whole core vault.
- Atomic remote manifests and verified per-item retry state.

## Safety notes
- Retrieval may now be blocked if there are pending local changes. Upload from that device first, or save a recovery backup and deliberately resolve the state before retrieval.
- The first persistence after upgrading may establish stable IDs for legacy records. Verify data in staging before production deployment.
- Keep v3.49.0 in staging and retain v3.48.0 plus encrypted backups until the manual test guide passes.
